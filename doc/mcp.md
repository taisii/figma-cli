# MCP 化の検討と設計メモ

## 背景

既存構成では、会話エンジン（例: Codex CLI）が Python の関数を直接呼び出す前提でした。LLM
統合を幅広く行いたい場合、ツール呼び出しの標準化が課題となるため Model Context Protocol
(MCP) への対応を検討しました。

## 検討ポイント

- **再利用性**: MCP 準拠により、Codex CLI 以外の MCP 対応 LLM クライアントからも同一の
  エンドポイントを利用可能になります。
- **純粋ツール方針との整合性**: 既存の `src.tools.research` は副作用を限定した純粋ツール群
  なので、MCP の Tool 呼び出しからラップするだけで方針を維持できます。
- **保守性**: サーバー層を薄いアダプタとして実装し、ビジネスロジックを既存の関数に集約す
  ることで、テストや将来の変更範囲を局所化できます。
- **依存関係**: MCP 実装は外部パッケージに依存するため、`pip install modelcontextprotocol`
  を追加手順として明示しました。ランタイム依存を optional に保つため、インポート時に
  明示的なエラーメッセージを出す構成としています。

## 実装方針

- `src/mcp_server.py` を追加し、`src.tools.research` の各関数を MCP Tool として公開。
- Tool 定義は JSON Schema を用いてパラメータ仕様を明記し、LLM クライアントからの
  バリデーションに寄与。
- `python -m src.mcp_server` で標準入出力ベースの MCP サーバーを起動可能。
- README に利用手順を追記し、MCP と従来 CLI 両方の利用シナリオをサポート。

## 今後の拡張案

- 認証やアクセス制御が必要な場合は、標準入出力以外のトランスポート（WebSocket など）
  への対応を検討する。
- Tool 呼び出しのメトリクスやログ出力を追加し、利用状況の可視化を行う。
- MCP クライアント向けのセットアップスクリプト（例: manifest ファイル）の用意。
